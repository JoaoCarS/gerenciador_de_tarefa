7. Ordem de desenvolvimento
Eu seguiria esta sequência para evitar começar pelo frontend sem ter as regras do sistema definidas.

Estrutura inicial: configurar o frontend, o backend, o TypeScript e o PostgreSQL.

Banco de dados: criar as tabelas, os relacionamentos e as migrations.

Autenticação: implementar cadastro, login, logout e middleware de autenticação.

CRUD: desenvolver e testar os endpoints de tarefas, incluindo a autorização por usuário.

Frontend: criar as telas, conectar a API e tratar erros e estados de carregamento.

Dashboard e filtros: adicionar as consultas de resumo e a organização das tarefas.

Testes e publicação: verificar o isolamento dos usuários, validar formulários e publicar a aplicação.

8. O que deixar fora do projeto
Para manter o escopo pequeno, eu não incluiria inicialmente:

Microsserviços ou arquitetura distribuída.

Redis, filas e processamento em background.

WebSockets e notificações em tempo real.

Compartilhamento de tarefas entre usuários.

Sistema de equipes e permissões complexas.

Aplicativo mobile separado.

Esses recursos não são necessários para demonstrar domínio de CRUD, autenticação, banco relacional e integração full stack.

Como saber se o projeto está pronto?
Considere o MVP concluído quando você conseguir cadastrar um usuário, entrar no sistema, criar e editar tarefas, atualizar seu status, excluir registros e confirmar que um segundo usuário não consegue acessar os dados do primeiro.

Esse é o escopo que eu adotaria: pequeno o suficiente para concluir sozinho, mas completo o bastante para praticar o fluxo real entre frontend, API, autenticação e banco de dados.

4. Qual abordagem Django escolher?
Existem duas opções válidas:

Opção A — Django completo

Django Templates + Forms + Views + ORM + autenticação nativa.

Minha recomendação para começar: menos configuração e aprendizado mais direto.

Opção B — Django REST Framework + React

Django fornece uma API REST e React cuida da interface.

Escolha se também quiser praticar APIs e a integração entre aplicações separadas. É um pouco mais complexo.

Minha sugestão é começar pela Opção A e, se quiser ampliar o aprendizado depois, transformar o backend em uma API com Django REST Framework.

Uma última recomendação: use LoginRequiredMixin ou login_required nas páginas privadas e valide a propriedade de cada objeto no servidor. Autenticar alguém e autorizar essa pessoa a acessar um registro são coisas diferentes.

Passo 7 — Implementar o CRUD
Abra tasks/views.py e adicione:

python
from django.contrib.auth.decorators import login_required
from django.shortcuts import get_object_or_404, redirect, render

from .forms import TaskForm
from .models import Task


@login_required
def task_list(request):
    tasks = Task.objects.filter(user=request.user)

    return render(
        request,
        "tasks/task_list.html",
        {"tasks": tasks},
    )


@login_required
def task_detail(request, pk):
    task = get_object_or_404(
        Task,
        pk=pk,
        user=request.user,
    )

    return render(
        request,
        "tasks/task_detail.html",
        {"task": task},
    )


@login_required
def task_create(request):
    form = TaskForm(request.POST or None)

    if request.method == "POST" and form.is_valid():
        task = form.save(commit=False)
        task.user = request.user
        task.save()
        return redirect("task_list")

    return render(
        request,
        "tasks/task_form.html",
        {"form": form, "title": "Nova tarefa"},
    )


@login_required
def task_update(request, pk):
    task = get_object_or_404(
        Task,
        pk=pk,
        user=request.user,
    )
    form = TaskForm(request.POST or None, instance=task)

    if request.method == "POST" and form.is_valid():
        form.save()
        return redirect("task_list")

    return render(
        request,
        "tasks/task_form.html",
        {"form": form, "title": "Editar tarefa"},
    )


@login_required
def task_delete(request, pk):
    task = get_object_or_404(
        Task,
        pk=pk,
        user=request.user,
    )

    if request.method == "POST":
        task.delete()
        return redirect("task_list")

    return render(
        request,
        "tasks/task_confirm_delete.html",
        {"task": task},
    )
Essas views implementam as cinco operações principais:

task_list: listar.

task_detail: visualizar.

task_create: criar.

task_update: editar.

task_delete: excluir.

Importante: todas as consultas de registros individuais verificam também user=request.user. Isso impede que um usuário autenticado acesse tarefas alheias alterando o identificador na URL.

1. O que significa startapp?
O Django permite dividir um projeto em aplicações menores, cada uma com uma responsabilidade específica.

startapp é o comando que cria uma aplicação Django.

tasks é o nome da primeira aplicação.

accounts é o nome da segunda aplicação.

manage.py é o arquivo que permite executar comandos administrativos do Django.

2. O que cada aplicação fará?
tasks — Gerenciamento de tarefas

Responsável pelo CRUD das tarefas.

models.py: define a entidade Task.

views.py: contém a lógica para listar, criar, editar e excluir tarefas.

forms.py: define os formulários das tarefas.

urls.py: define os endereços das páginas.

accounts — Cadastro e autenticação

Responsável pelas páginas de cadastro e pelos fluxos relacionados à conta.

forms.py: formulário de cadastro.

views.py: lógica para registrar usuários.

urls.py: endereços de cadastro e autenticação.

O login e o logout podem usar as funcionalidades já fornecidas pelo Django.

├── models.py
├── tests.py
└── views.py
Ao executar o segundo comando, ele cria uma estrutura equivalente dentro de accounts/.

Alguns arquivos, como forms.py e urls.py, não são criados automaticamente. Você poderá criá-los manualmente quando precisar.

4. Por que não colocar tudo em uma aplicação só?
Você poderia colocar o projeto inteiro em uma única aplicação. Isso funcionaria perfeitamente para um projeto pequeno.

tasks cuida das tarefas.

accounts cuida do cadastro.

O Django Auth cuida da infraestrutura de autenticação.

Importante: criar uma aplicação não significa criar uma entidade no banco de dados. No seu projeto, você terá apenas um model próprio de negócio, Task. A aplicação accounts não exige que você crie um model de usuário, pois o Django já fornece um.

Depois de criar as duas aplicações, lembre-se de adicioná-las a INSTALLED_APPS no arquivo config/settings.py para que o Django as reconheça.
